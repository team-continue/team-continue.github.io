# ロボコンチーム公式サイト デザイン・UI・実装要件書

## 1. 目的

本書では、ロボコンチーム公式サイトの以下の要件を定義する。

- デザイン方針
- 共通UI
- ヘッダー
- 左ドロワーメニュー
- 検索UI
- レスポンシブ対応
- SEO
- GitHub Pages対応
- README
- 実装確認
- 実装優先順位

---

## 2. デザイン方針

ロボコンチームの公式サイトとして、技術感があり、見栄えのするかっこいいデザインにする。

方向性としては、以下を組み合わせたような雰囲気を目指す。

- 技術スタートアップのコーポレートサイト
- ロボット開発チームのポートフォリオサイト
- エンジニアリングブログ
- 研究プロジェクト紹介サイト

---

## 3. ビジュアル方針

以下を意識してデザインする。

- 技術系チームらしい先進的な印象にする
- ロボット開発・自律移動・制御・メカ設計を想起させる雰囲気にする
- 黒、ダークネイビー、グレー、白などを基調にする
- アクセントカラーとしてシアン、ブルー、ライム、オレンジなどを効果的に使用する
- 余白を広めに取り、情報が詰まりすぎないレイアウトにする
- カード型UI、グリッドレイアウト、タグ表示を活用する
- HOMEのファーストビューは特に印象的にする
- プロジェクトやブログ記事のカードは、画像・タグ・説明文が映えるデザインにする
- メンバー紹介は、写真が映えるプロフィールカードにする
- hover時の自然な動きや軽いトランジションを入れる
- スマホ表示でも崩れず、読みやすくする
- フォントサイズ、行間、余白に気を配り、安っぽく見えないようにする

ただし、過度なアニメーションや複雑すぎる演出は不要とする。

「かっこよさ」と「情報の探しやすさ」を両立する。

見た目は仮実装ではなく、初期公開できる程度の完成度を目指す。

---

## 4. 共通レイアウト要件

すべてのページで、以下の共通レイアウトを使用する。

- Header
- Main content
- Footer

HeaderとFooterは全ページ共通にする。

ページごとにSEO用の以下を設定できるようにする。

- title
- description

---

## 5. ヘッダー要件

通常の横並びグローバルナビゲーションではなく、全ページ共通で「左上のハンバーガーメニューボタン」から「左側に開くドロワーメニュー」でページ遷移するUIにする。

Headerは以下の構成にする。

- 左端：ハンバーガーメニューボタン
- 左寄り：チームロゴまたはチーム名
- 右端：検索ボタン

Headerの仕様は以下とする。

- Headerは全ページ共通にする
- Headerはページ上部にsticky表示する
- Headerの背景は、半透明の黒またはダークネイビーにする
- Headerには軽いblurや細い境界線を入れる
- チームロゴまたはチーム名をクリックするとHOMEに遷移する
- スマホでも押しやすいように、各ボタンのタップ領域を十分に確保する
- Headerには横並びの通常グローバルナビゲーションを置かない

ただし、プロジェクト詳細ページ内のローカルタブナビゲーションは表示してよい。

---

## 6. ドロワーメニュー要件

ハンバーガーメニューボタンをクリックすると、画面左側からドロワーメニューがスライドインする。

ドロワーメニューには以下のリンクを表示する。

```txt
HOME
PROJECT
  CoRE 2025
    トップ
    メカ
    回路・電装
    ソフトウェア
  CoRE 2026
    トップ
    メカ
    回路・電装
    ソフトウェア
  その他プロジェクト
MEMBERS
SNS・LINK
BLOG
```

ドロワーメニューの仕様は以下とする。

- 左側から開く
- 背景には半透明のオーバーレイを表示する
- オーバーレイをクリックするとメニューを閉じる
- Escキーを押すとメニューを閉じる
- メニュー内に閉じるボタンを配置する
- 現在表示中のページがわかるように、アクティブなリンクを強調表示する
- PROJECT配下は階層構造がわかるようにインデントして表示する
- スマホでも押しやすいように、リンクの余白を十分に取る
- hover時や開閉時には自然なトランジションを入れる
- 黒またはダークネイビーを基調にし、技術感のあるデザインにする

---

## 7. プロジェクト内ローカルナビゲーション要件

各プロジェクトページの上部には、同じプロジェクト内のページを切り替えるためのローカルタブまたはローカルナビゲーションを表示する。

表示例：

```txt
[トップ] [メカ] [回路・電装] [ソフトウェア]
```

現在表示中のページがわかるようにする。

Headerには横並びの通常グローバルナビゲーションを置かないが、このローカルナビゲーションは表示してよい。

---

## 8. 簡易検索UI要件

右端の検索ボタンをクリックすると、サイト内検索用の簡易検索UIを開く。

検索機能は簡易実装でよい。

---

### 8.1 検索対象

検索対象は以下とする。

- ブログ記事
- プロジェクト（プロジェクトトップページ）
- プロジェクトセクション（メカ／回路・電装／ソフトウェアの各ページ）
- メンバー
- その他プロジェクトページ

---

### 8.2 検索対象項目

検索対象の項目は以下とする。

- タイトル
- 概要
- タグ
- カテゴリ
- 著者名
- メンバー名
- 役割

---

### 8.3 検索UIの表示内容

検索UIは、モーダルまたは上部から開く検索パネルとして実装する。

検索UIには以下を表示する。

- 検索入力欄
- 検索結果一覧
- 各検索結果のタイトル
- 種別
  - Blog
  - Project
  - ProjectSection
  - Member
  - Page
- 概要
- 該当ページへのリンク

---

### 8.4 検索仕様

本文全文検索までは不要とする。

外部検索サービスや外部APIは使用しない。

ローカルのコンテンツデータをもとにしたクライアントサイド検索でよい。

以下は不要とする。

- 日本語の形態素解析
- 曖昧検索
- 全文検索
- 検索インデックス生成
- 外部API連携

単純に、入力文字列が以下に含まれているかを判定する実装でよい。

- タイトル
- 概要
- タグ
- カテゴリ
- 著者名
- メンバー名
- 役割

キーワード未入力時は、最新ブログ記事や主要プロジェクトを候補として表示する。

`draft: true` のブログ記事は検索結果に表示しない。

---

### 8.5 検索UIの操作要件

検索UIは以下を満たす。

- 検索ボタンを押すと開く
- Escキーで閉じる
- 背景オーバーレイをクリックすると閉じる
- 検索UIを開いたら入力欄に自動フォーカスする
- スマホでも使いやすいレイアウトにする
- ダークネイビーまたは黒基調のデザインにする
- サイト全体のデザインと統一する

---

## 9. カードUI要件

以下の要素はカード形式で表示する。

- プロジェクトカード
- ブログ記事カード
- メンバーカード
- SNS・リンクカード
- その他プロジェクトカード

カードには必要に応じて以下を表示する。

- タイトル
- 概要
- 画像
- タグ
- カテゴリ
- 日付
- 著者
- 詳細ページへのリンク

画像がない場合は、プレースホルダー画像またはCSSで作成したプレースホルダー表示を使う。

---

## 10. レスポンシブ対応要件

すべてのページでレスポンシブ対応を行う。

以下を満たすこと。

- スマホ表示で横スクロールが発生しない
- Headerのボタンが押しやすい
- ドロワーメニューのリンクが押しやすい
- 検索UIがスマホでも使いやすい
- カードレイアウトが画面幅に応じて1列、2列、3列などに変化する
- 文字サイズ、行間、余白がスマホでも読みやすい
- 画像がコンテナからはみ出さない

---

## 11. アニメーション・トランジション要件

過度なアニメーションは不要とする。

ただし、以下には自然なトランジションを入れる。

- ボタンhover
- カードhover
- ドロワーメニュー開閉
- 検索UI開閉
- リンクhover
- タブ切り替えのアクティブ表示

アニメーションは軽量にし、情報の見やすさを損なわないようにする。

---

## 12. SEO要件

各ページで以下を設定できるようにする。

- title
- description

ブログ記事やプロジェクトページでは、コンテンツデータからtitleとdescriptionを生成してよい。

最低限、以下のページは適切なtitleとdescriptionを持つこと。

- HOME
- PROJECT一覧
- 各プロジェクトページ
- MEMBERS
- SNS・LINK
- BLOG一覧
- 各ブログ記事ページ

---

## 13. 実装上の注意

以下を満たすように実装する。

- できるだけコンポーネントを再利用する
- 画像がない場合はプレースホルダー画像を表示する
- すべてのページでレスポンシブ対応する
- SEO用に `title` と `description` を設定できるようにする
- Headerには横並びの通常グローバルナビゲーションを置かない
- Headerにはハンバーガーメニュー、チームロゴまたはチーム名、検索ボタンを配置する
- Footerには、チーム名、SNSリンク、GitHubリンク、コピーライトを表示する
- コードは読みやすく整理する
- README.mdに、記事・プロジェクト・メンバーの追加方法を書く
- `draft: true` の記事は本番表示から除外する
- 画像パスやリンクが未設定でもビルドエラーにならないようにする
- 実装技術に依存しすぎない構成にする

---

## 14. Footer要件

Footerには以下を表示する。

- チーム名
- 簡単な説明文
- SNSリンク
- GitHubリンク
- コピーライト

Footerもサイト全体のデザインと統一する。

## 15. GitHub Pages対応

GitHub Pagesで公開できるように、以下を設定する。

- 静的ビルド設定
- GitHub Actionsによる自動デプロイ設定
- README.mdへのデプロイ方法の記載

GitHub Pagesで `username.github.io/repository-name` に公開する場合は、ベースパスに注意する。

例：

```txt
https://username.github.io/repository-name/
```

この場合、サイト内リンクや画像パスが `/repository-name/` 配下で正しく動作するようにする。

ユーザーまたは組織サイトとして以下に公開する場合は、ベースパスは `/` でよい。

```txt
https://username.github.io/
```

README.mdに以下を記載する。

```md
GitHub Pagesで username.github.io/repository-name に公開する場合は、
ベースパスを /repository-name/ に設定してください。

username.github.io 直下に公開する場合は、
ベースパスを / にしてください。
```

---

## 16. GitHub Actions要件

GitHub Pagesへ自動デプロイできるワークフローを作成する。

以下を満たす。

- `main` ブランチへのpushでビルド・デプロイする
- Node.jsを使用する場合はNode.jsをセットアップする
- 依存関係をインストールする
- ビルドコマンドを実行する
- 生成された静的ファイルをGitHub Pagesへデプロイする

## 19. 実装確認

実装後、以下に相当する処理が通ることを確認する。

```bash
依存関係のインストール
ビルド
```

Node.js系の実装であれば、以下が通ることを確認する。

```bash
npm install
npm run build
```

エラーが出た場合は修正する。

実装を始める前に、現在のディレクトリ構成を確認し、既存ファイルがある場合は壊さないようにする。

既存プロジェクトでない場合は、新規Webサイトプロジェクトとして初期化する。

## 20. 実装優先順位

実装範囲が大きい場合は、まず以下を優先する。

1. ページ構成とルーティング
2. コンテンツデータ定義
3. Header、左ドロワーメニュー、Footer
4. プロジェクトページとブログ記事の紐づけ
5. 簡易検索UI
6. デザイン調整

---

## 21. 重要な実装方針まとめ

- Headerには横並びグローバルナビを置かない
- ハンバーガーメニューから左ドロワーメニューを開く
- ドロワーメニューは全ページ共通にする
- 検索UIは簡易的なクライアントサイド検索でよい
- 検索対象はブログ、プロジェクト、メンバー、その他ページとする
- `draft: true` の記事は全表示箇所から除外する
- 画像がない場合はプレースホルダーを表示する
- すべてのページでレスポンシブ対応する
- GitHub Pagesのベースパス設定に注意する
- デザインは初期公開できる程度に整える
